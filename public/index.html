UpgradeLens Verification Scope & Honest Limitations

1. Differences Are Not Always Bugs: An altered post-upgrade observation can be an approved feature. Scenarios must explicitly authorize changes with expected bounds.
2. Identical Outputs Do Not Prove Safety: Passing all checks proves only that observed functions returned expected values; unexercised execution branches or state transitions may still regress.
3. Bounded Coverage Scope: Evaluates only configured actors, arguments, and read-only (view/pure) functions in the V1 ABI. V2-only views are never compared, and state-modifying functions are excluded.
4. Expected-Change Bounds: Expected-change bounds are tuned to this demo and could hide a regression inside the allowed band.
5. Constructed Bug Patterns: The partial-bug V2 is a constructed tier-boundary example, not a measured-frequency claim.
6. Tooling Overlap Context: Statements about Diffusc and other tools are from memory, not verified in this project. UpgradeLens focuses on snapshot comparison on the exact same proxy across an upgrade transaction.
